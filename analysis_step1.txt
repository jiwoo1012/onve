1단계 현재 코드 분석
작성일: 2026-07-29
분석 범위: 코드 변경 없이 현재 구조와 Firebase 전환 지점을 확인함.

1. 현재 폴더 구조
- shoppingmall/: 실제 Vite React 애플리케이션 루트(package.json, vite.config.js 포함)
- shoppingmall/src/: React 소스
  - components/: 재사용 UI 컴포넌트와 각 컴포넌트의 .module.scss
  - pages/: 화면 단위 컴포넌트와 각 페이지의 .module.scss
  - firebase/: Firebase 초기화 및 도메인별 API 모듈
  - store/: Zustand store 초안 파일
  - hooks/, utils/, constants/: 공통 훅, 유틸리티, 상수
  - assets/: 번들 대상 이미지
- shoppingmall/public/: 정적 파일
  - data/products.json: 현재 상품 원본 데이터
  - data/notices.json, events.json, categories.json, banners.json: 기타 정적 데이터
  - img/: 상품/배너/아이콘 이미지
- shoppingmall/.env: Firebase 환경변수 파일(실제 값은 분석·기록하지 않음)
- 상위 C:\react\shoppingmall/: 별도의 package.json과 node_modules가 있으나, Vite 앱 패키지는 shoppingmall/package.json임.

2. 상품 JSON을 불러오는 위치
- src/pages/Home.jsx: fetch('/data/products.json') 후 salesCount 기준 상위 4개를 메인 베스트 상품으로 사용.
- src/pages/Products.jsx: fetch('/data/products.json') 후 카테고리 필터와 정렬에 사용.
- src/pages/ProductDetail.jsx: fetch('/data/products.json') 후 URL id와 일치하는 상품을 조회.
- 따라서 상품 데이터 Firestore 전환 시 위 3개 페이지의 데이터 로딩을 공통 API/훅으로 교체해야 함.

3. 로그인과 회원가입 페이지를 불러오는 위치
- src/App.jsx에서 /login -> pages/Login.jsx, /signup -> pages/SignUp.jsx로 라우팅.
- Header.jsx의 로그인/회원가입 아이콘 링크도 각각 /login, /signup을 사용.
- Login.jsx는 firebase/auth의 signInWithEmailAndPassword와 firebase/firebase.js의 auth를 직접 사용하고 성공 시 /mypage로 이동.
- SignUp.jsx는 createUserWithEmailAndPassword, updateProfile을 직접 사용하고 성공 시 /mypage로 이동.

4. 라우터 구조
- src/main.jsx: BrowserRouter로 App을 감쌈.
- src/App.jsx: 공통 Header, main 내부 Routes, 공통 Footer 구조.
- 공개 라우트: /, /products, /products/:id, /products/category/:category, /cart, /login, /signup, /mypage, /wishlist, /notice, /notice/:id, /search/:keyword.
- 그 외 경로: /* -> NotFound.
- ProtectedRoute.jsx는 Firebase 인증 상태를 확인해 비로그인 사용자를 /login으로 이동시키지만, 현재 App.jsx의 라우트에는 적용되어 있지 않음.
- Admin.jsx, AdminProduct.jsx, AdminOrder.jsx 및 AdminRoute.jsx는 존재하지만 현재 App.jsx에 관리자 라우트가 등록되어 있지 않음. AdminRoute.jsx도 아직 접근 제어 구현이 없음.

5. Zustand 사용 여부
- 상위 package.json에는 zustand 의존성이 있으나, 실제 Vite 앱인 shoppingmall/package.json에는 zustand가 없음.
- src/store/authStore.js만 create를 import한 초안 상태이며 구현과 사용처가 없음.
- productStore.js, cartStore.js, wishlistStore.js, orderStore.js, loadingStore.js 파일도 존재하지만 현재 페이지/컴포넌트에서 import하거나 사용하는 코드가 확인되지 않음.
- 결론: 현재 실행 기능은 Zustand를 사용하지 않으며, Zustand 도입 전 실제 앱 패키지 의존성 및 store 설계를 정리해야 함.

6. Firebase 연결 시 수정 또는 추가가 필요한 파일
- src/firebase/firebase.js: Firebase 초기화 지점. 환경변수 참조는 유지하고 API 키 출력용 console.log는 제거 대상.
- src/firebase/productApi.js: 빈 파일. 상품 Firestore CRUD/query API 구현 위치.
- src/firebase/orderApi.js, noticeApi.js, userApi.js, storageApi.js: 각 도메인 Firebase API 구현 위치(현재 대부분 빈 파일).
- src/firebase/authApi.js: 인증 API를 이 파일로 모을 경우 Login.jsx, SignUp.jsx의 직접 Firebase SDK 호출을 이전.
- src/pages/Home.jsx, Products.jsx, ProductDetail.jsx: products.json 직접 fetch를 productApi 또는 공통 훅 호출로 교체.
- src/pages/Login.jsx, SignUp.jsx, MyPage.jsx, components/ProtectedRoute.jsx: 인증 API 및 사용자 문서 연동 시 수정 대상.
- src/App.jsx, components/AdminRoute.jsx: 관리자 라우트 등록 및 관리자 권한 검사 구현 대상.
- 신규 필요 가능 파일: .env.example(키 이름만), firestore.rules 또는 Firebase Console에 적용할 규칙 문서, 필요 시 src/hooks/useProducts.js 등 공통 데이터 훅.
- Firebase Storage를 사용할 때에는 firebase.js에서 getStorage export를 추가하고 storageApi.js를 구현.

7. 기존 기능·디자인을 유지하는 작업 순서 및 작성 규칙
1) products.json의 상품 필드(id, name, price, discountRate, category, image, stock, salesCount, createdAt 등)를 확인하고 Firestore 문서 구조를 동일하게 설계.
2) Firebase 환경변수는 실제 값을 기록하거나 코드에 직접 입력하지 않고 import.meta.env.VITE_* 참조를 유지. firebase.js의 민감정보 console.log는 제거.
3) productApi.js에 읽기 API부터 구현하고 Home/Products/ProductDetail의 fetch 로직만 단계적으로 교체. 화면의 props, 정렬, 필터, 로딩 및 오류 UI는 유지.
4) Firestore 보안 규칙을 먼저/동시에 작성하여 고객 읽기, 본인 데이터 접근, 관리자 쓰기 권한을 명시. 규칙 없이는 관리자 기능을 완료 처리하지 않음.
5) 인증 상태를 공통화한 뒤 ProtectedRoute를 마이페이지·주문 등 로그인 필요 라우트에 적용. 관리자 역할은 사용자 문서 또는 Custom Claims 기반으로 검증하고 AdminRoute에 적용.
6) 관리자 상품/주문/공지 CRUD 및 Storage 이미지 업로드를 작은 단위로 추가하고 각 단계에서 권한별 테스트 수행.
7) 기존 컴포넌트 작성 방식(함수형 React 컴포넌트, hooks 기반 상태/효과, default export)을 유지. 각 JSX와 동일한 이름의 .module.scss를 import하여 styles.className 형태를 유지하며 전역 CSS 또는 인라인 스타일 추가를 피함.
8) 변경 단계마다 historyCode.txt에 수정 이유, 대상 파일, 테스트 결과를 기록. Firebase 기능 변경 단계에는 테스트용 보안 규칙 코드도 함께 기록.

확인된 주의 사항
- 화면에 표시되는 일부 한글이 콘솔상 인코딩 손상된 형태로 확인되나, 2026-07-29 production build는 성공했음. 실제 브라우저 표시와 lint도 Firebase 작업 전/후 별도로 확인하고, 오류가 확인된 경우 별도 수정 내역으로 기록해야 함.
- Firestore의 기본 보안 규칙은 현재 요청에서 지정된 전체 거부 규칙이며, 관리자 기능 구현 시 데이터 구조와 권한 정책에 맞는 구체 규칙으로 교체 및 테스트가 필요함.

빌드 확인
- 실행: npm run build (shoppingmall/)
- 결과: 성공. 107개 모듈 변환, production bundle 생성 완료.
